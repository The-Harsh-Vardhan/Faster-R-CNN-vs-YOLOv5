## A. Introduction

### Objective

Train and evaluate a **Faster R-CNN** detector on **Pascal VOC 2012** and interpret its behavior in terms of detection quality and inference speed for team-level comparison with YOLO models.

### Problem Statement

Perform **multi-class object detection**: for each input image, predict object bounding boxes and class labels from Pascal VOC categories.

### Why Faster R-CNN for this contribution

The selected architecture was `torchvision.models.detection.fasterrcnn_resnet50_fpn_v2` because:

- It is a strong, research-grade **two-stage detector**.
- It provides better proposal-based reasoning than one-stage detectors in many complex scenes.
- Torchvision integration allows rapid implementation with robust defaults.
- It is a meaningful counterpart to YOLO in the project's accuracy-speed trade-off analysis.

## B. Dataset Analysis (Pascal VOC 2012)

### Dataset Description

Pascal VOC 2012 is a classical object detection benchmark with **20 foreground classes** and XML-based bounding box annotations.

- Images path pattern: `VOC2012/JPEGImages`
- Annotation path pattern: `VOC2012/Annotations/*.xml`
- Split files used: `ImageSets/Main/train.txt` and `ImageSets/Main/val.txt`

### Classes used in code

The notebook explicitly maps these 20 classes:

`aeroplane, bicycle, bird, boat, bottle, bus, car, cat, chair, cow, diningtable, dog, horse, motorbike, person, pottedplant, sheep, sofa, train, tvmonitor`

### Effective split used in experiment

The notebook sub-samples the official split lists for practical runtime:

- Train IDs used: first **2000** from `train.txt`
- Validation IDs used: first **500** from `val.txt`

### Annotation processing

From each XML file, object tags are parsed and converted into detection targets:

- Bounding boxes loaded from `xmin, ymin, xmax, ymax`
- Invalid boxes (`x2 <= x1` or `y2 <= y1`) are ignored
- Class names are mapped to integer labels (`1..20`)
- Background class is handled internally by Faster R-CNN head design

## C. Model Architecture — Faster R-CNN (Pascal Setup)

### 1. Backbone and Feature Pyramid

The model uses `fasterrcnn_resnet50_fpn_v2(weights="DEFAULT")`:

- ResNet-50 backbone for hierarchical visual features
- FPN for multi-scale representation
- Suitable for objects of varying sizes in VOC scenes

### 2. Region Proposal Network (RPN)

The RPN proposes candidate object regions over feature maps using anchors and objectness scoring.

### 3. ROI Head

For each proposal, ROI features are classified and box coordinates are refined.

### 4. Task-specific head replacement

The default predictor is replaced with:

- `FastRCNNPredictor(in_features, 21)`

Reason:

- 20 VOC object classes + 1 background class = 21 outputs.

### 5. Input transform tweak

The model transform minimum size is set to:

- `model.transform.min_size = (400,)`

This controls the detector's internal resizing policy during forward passes.

## E. Training Analysis

### Training loop structure

For each epoch:

1. Run one full training epoch (`train_one_epoch`)
2. Evaluate on validation data (`evaluate`)
3. Record:
   - `map50` (`map_50`)
   - `map5095` (`map`)
   - epoch time in seconds
4. Append to history and export as CSV at the end

### Loss behavior (algorithmic)

Loss is the summed detection multi-task objective returned by Torchvision:

- classification and localization terms from RPN and ROI stages

The notebook logs average training loss per epoch and prints mAP@0.50 for progress tracking.

### Fine-tuning behavior

This is **fine-tuning**, not feature extraction:

- Pretrained weights are loaded (`weights="DEFAULT"`)
- Layers are not explicitly frozen
- Therefore, trainable model parameters are updated on VOC data

## F. Performance Evaluation

### Metrics computed

The evaluation function uses `MeanAveragePrecision()` and reports:

- `map` (COCO-style mAP@0.50:0.95)
- `map_50` (mAP@0.50)

### Speed benchmarking

Speed is measured over up to 31 validation batches:

- GPU synchronization before and after inference timing
- Mean latency returned in milliseconds
- FPS computed as reciprocal of per-batch inference time

### Reported Pascal VOC comparison summary (team report values)

| Model                     | mAP@0.50 |   FPS |
| ------------------------- | -------: | ----: |
| Faster R-CNN (Pascal VOC) |   0.6934 |  5.81 |
| YOLO (Pascal VOC)         |   0.7459 | 50.12 |

Interpretation:

- YOLO is significantly faster in this setup.
- Faster R-CNN remains methodologically important for two-stage detection quality analysis and proposal-driven reasoning.

## H. Limitations

1. **Subsampled training split** (2000/500) may not reflect full-dataset convergence behavior.
2. **Short training budget** (5 epochs) limits deeper optimization.
3. **No explicit augmentation pipeline** (flip, color jitter, etc.) in current notebook.
4. **Single detector configuration** tested (one LR/optimizer schedule).
5. **Per-class AP analysis** is not explicitly exported in this notebook script.

## J. Conclusion

This contribution successfully implemented an end-to-end **Faster R-CNN on Pascal VOC** pipeline covering:

- dataset parsing from VOC XML,
- pretrained model adaptation to VOC classes,
- fine-tuning with mixed precision,
- quantitative evaluation with mAP and speed,
- and qualitative visualization export.

In the team comparison context, the key takeaway is the expected deployment trade-off:

- **YOLO** is superior for real-time constraints due to high FPS,
- while **Faster R-CNN** remains a strong two-stage baseline for detailed detection analysis and precision-focused workflows.

The final model choice should therefore be **requirement-driven** (latency-critical vs. quality/analysis-critical), not architecture-driven alone.
